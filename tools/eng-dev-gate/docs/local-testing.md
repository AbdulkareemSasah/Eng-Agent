# Local testing: eng-dev-gate

Nothing in the skeleton (plan task T1) needs a host program. Items below are added by later tasks.

- Real GitHub Actions runs of the composite actions (task T6) and the Windows CI job: needs a CI run.
- The `check` command runs real `uv`, ruff and mypy; only its integration tests (toy workspace in a temporary directory, no network, no host program) cover that, so nothing here needs a host program (task T5).
- The `tests` step runs real coverage.py and pytest on a toy member in a temporary directory (no network, no host program), so nothing here needs a host program (task T7).
- Base-commit gate (task T26, needs a real CI run once T6 has wired the jobs): that `uv run --project <gate-root> --package eng-dev-gate eng-gate --root . --gate-root <gate-root> <command>` runs the base gate in its own environment while the head environment runs the code under test; that `hashFiles` in a step `if:` sees `.gate-base`; that `PYTHONPATH` puts the base plugin ahead of an editable install of the head; and that the event file's `base.sha` equals `git rev-parse HEAD` of the `.gate-base` checkout (the CF009 provenance rule). The tests use temporary repositories and a redirected running package; they do not show any of this.
- CI part 1 (task B-035, plan task T6; every item needs a real GitHub Actions run, none was run in the build environment): that the workflow and the four composite actions (`setup`, `gate`, `agents-drift`, `build`) are accepted by Actions, including a local `uses: ./.gate-base/...` path and `hashFiles` in a step `if:` (the first pull request after the merge runs the head variants and reports AW09, the next one the base variants); the action SHAs of `actions/checkout` and `astral-sh/setup-uv` were copied from the B-002 skeleton and could not be looked up again with the GitHub tools of the build session; that `uv build --package <name>` builds each member in the workspace root; that `uv run pytest` at the root (interim step of the `gate` action until task T7) behaves as in the skeleton; the first `windows` job run on a push to `build/v1` with the `setup` action under `bash` on `windows-latest`.
- Security job (task B-047, plan task T18; needs a real CI run): that `uv audit --locked` runs in Actions with network access and which exit codes it returns for a finding and for an unreachable advisory service (the action treats any non-zero exit as failure); that the `security` job accepts the `scan` array and `BASE_SHA..HEAD` on a pull request with `fetch-depth: 0`; the first pull request after the merge runs the head variant and reports AW09.
- `windows-tests` and the `windows` job (task B-052, plan task T23; needs a real CI run on `windows-latest` after a push to `build/v1`): that the `windows` action works with the `setup` action's environment under `bash`, that `uv run --project <root> --locked --all-packages --group dev python -m pytest <paths>` runs the declared paths with Windows paths and line endings, and that exit code 5 (nothing collected) reports ST001. The unit tests use a recording runner and a toy workspace; they run no Windows tests.
- `licenses` and `docs-fresh` (task B-048, plan task T19): no host program. Not shown by the tests: the result on a CI runner's real environment (license metadata is read from the environment as installed there); generator output is compared as the tool runner returns it (standard output and error merged), so a generator that writes to standard error would need the runner to separate the streams.
- Mutation step (task T20, B-049): that mutmut refuses to run on Windows as ADR-0002 states, so the step reports MU002 (a notice locally, exit 3 with `CI` set); and the first run of `eng-gate check` for a package with R1 or R2 modules in a pull request, where the base commit comes from the event file. Only Linux was exercised, with a toy package in a temporary directory (no host program).
- `review` and the `ci-review` job (task B-051, plan task T22; needs a real CI run, none was run in the build environment): that the job and its action `ci-review` are accepted by Actions and run the head variant (AW09) on the first pull request after the merge and the base variant afterwards; that the prompt files are included in the built wheel of `eng-dev-gate`. No provider is called: the reviewer providers and posting under the reviewer identity are not in 0.1 (owner decision OQ-3).
- `gate-check` job (task B-043, plan task T14; needs a real GitHub Actions run, none was run in the build environment): that `actions/checkout` with `fetch-depth: 0` leaves `origin/<gate branch>` for the default `--gate-ref`; that the `edited` trigger re-runs the job after a change of the pull request body; the first pull request after the merge runs the head variant of the action (AW09 is not printed by `gate-check` yet), the next one the base variant. The GC015 paths with bootstrap off wait for the approvals port (task T24).
- `test-first` part 1 (task B-045, plan task T16): no host program. The tests use temporary git repositories. Not shown by them: that the title read from the event file is the title squash merge uses on a real pull request; the runs and the base isolation come with task T17.
- Approvals port with bootstrap off (task B-053, plan task T24; needs the real identities and a real CI run; every test uses a fake port and a fake HTTPS connection): that `GET /repos/{repo}/pulls/{n}/reviews` with `GITHUB_TOKEN` (permission `pull-requests: read`) returns the reviews with `user.login`, `state` and `commit_id` as the adapter reads them, and that the `gate-check` job passes `GITHUB_TOKEN` and `GITHUB_REPOSITORY` to the command (the action file is outside this task; without them the command exits 2 with bootstrap off); that the reviewer app's approval is posted on the head commit under `identities.reviewer_app`. Not covered: the owner approval required for golden data, cited constants, templates and policies (G3, R1) and for a changed generated schema snapshot (R2) cannot be derived from the diff and is left to review.
- `test-first` part 2 (task B-046, plan task T17; needs the first real CI runs): that `PYTHONPATH` set to the base worktree's `src` folders beats the editable installs of the head environment, so the import probe (TF011) passes for every existing package; that `uv run --project <judged tree> --locked --all-packages --group dev python -m pytest` runs from a temporary worktree outside the checkout with the judged tree's environment; and the first run of the `test-first` job (the first pull request after the merge reports AW09 from the head variant, the next runs the base variant). The tests use temporary git repositories and the interpreter that runs them; only the argument list of the judged-environment command is checked. No host program is involved.
- `types` and `imports` in pull-request context (task B-347, plan task T32, AC54a; needs a real CI run after the first merge, when the base gate carries this change): that a pull request which adds a third-party dependency with its stub distribution (the case of PR 112, jsonschema and types-jsonschema) passes `types` and `imports` with the stubs and the distribution map of the judged environment, and that `uv run --locked --all-packages --group dev` resolves from the CI runner's package index. The tests use local path dependencies and the stub layout of `types-*` distributions; no host program is involved.
- Self-gate run (task B-054, plan task T25, AC64; needs a real CI run): that every job of the workspace is green on the pull request of the last task. Verified here only by running `eng-gate check --all` in head and pull-request mode; no host program is involved.
